# 麦麦的底层：活人感是怎么被工程化的

读了 `src/maisaka/`（新的推理引擎）、`src/learners/`、`src/chat/replyer/`
和 `prompts/zh-CN/*.prompt`。约 21 万行，核心机制集中在十几个小文件里。

**一句话结论：**

> 他们几乎没在优化「她说得像不像人」，
> 全部工程量压在**「要不要说、什么时候说、说完了效果如何」**上。

这跟我们的投入方向正好相反。我们把 12.5k tokens 的人设卡做到很细，
但她**永远秒回、永远回、永远精准回应**——这三条里任何一条，真人都做不到。

---

## 一、说话前面有四道闸，一道比一道贵

麦麦收到一条消息，到她真的说出话，中间隔着四层，每层都可能把她拦下来：

```
消息进来
  │
  ├─① focus 槽位     FOCUS_SLOT_LIMIT = 1     ← 她一次只能专注一个会话
  ├─② 空闲退避       指数退避，2^n            ← 刚才白忙一场，这次先躲一会
  ├─③ 回复必要性     打分 ≥ 80 才进 Planner   ← 见下
  └─④ Planner        导演视角，可以决定 wait  ← LLM 亲自判断
       │
       └─ reply 工具 ← 只有走到这才产生台词
```

前三道**一个 token 都不花**。这是设计上的关键：
真人的「不回你」大部分时候不是想过之后决定不回，是**根本没进入到「想」这一步**。

### 回复必要性评分（`maisaka/reply_necessity.py`）

```
最终分 = (强相关 + 内容 + 压力 - 存在感惩罚) × (0.5 + 0.5 × 频率)
阈值 = 80
```

| 项 | 分值 | 说明 |
|---|---|---|
| 强相关 | @ =100 / 提及=80 / 私聊=40 / focus=40 | 私聊只有 40，**私聊也不是必回** |
| 内容 | 问题 +15、请求 +20、征询意见 +20、长文本 +5/+10 | |
| | **短反应 −25** | 「哈哈」「嗯」「6」这种批量到来时倒扣 |
| 压力 | 积压量，阈值内平方增长、超出后对数增长，上限 100 | |
| | 空窗达到平均间隔 +15 | |
| **存在感惩罚** | **最多 −25** | ← 见下 |

**两个我认为最值钱的设计：**

**1. 存在感惩罚。** 统计最近 5 分钟她自己发言占总消息的比例：

```python
≤ 25%           不罚
25% → 60%       线性罚到 −25 分
```

翻译成人话：**她最近说太多了，就该闭嘴一会儿。**
这不是内容判断，是纯粹的节奏配额。真人的「话痨感」正是这个东西缺失造成的。

**2. 纯沉默永远不能触发她说话。**

`turn_gates.py` 里有个「空窗补偿」：你很久不说话，这段沉默会被折算成
「等效消息数」推着她开口。但折算量被硬性封顶在 `trigger_threshold - 1`：

```python
idle_equivalent_count = min(
    idle_seconds / average_message_interval,
    float(max(0, trigger_threshold - 1)),   # 永远差一条
)
```

代码注释写得很直白：「杜绝纯靠沉默累积反复唤醒回复」。
**至少要有一条真实新消息**，她才可能开口。
——这道闸挡住的是「AI 疯狂找话题」这个最出戏的失败模式。

## 二、她的注意力是稀缺资源

```python
FOCUS_SLOT_LIMIT = 1
```

同一时刻只有一个会话能进入决策循环，其他会话的消息进队列但不触发思考。

这条极其重要，而且**是 AI 女友最容易穿帮的地方**：
玩家心里清楚这个 AI 同时在陪一万个人。任何「随叫随到、无限精力」的表现
都在提醒他这一点。给她一个**有限的、会被占用的注意力**，
比给她写一百条人设都更接近活人。

配套的还有 `focus_cool_time`（退出 focus 后的冷却）和
`release_focus_and_block_next_entry`（因闲置退出的会话，**不许立刻抢回槽位**）。

## 三、她可以被打断

`reasoning_engine.py:1044` —— Planner 正在思考时来了新消息，抛 `ReqAbortException`：

```python
except ReqAbortException as exc:
    state.planner_interrupted = True
    interrupt_result = await self._handle_planner_interrupt(...)
    cached_messages = interrupt_result.retry_messages
    trigger_message = interrupt_result.retry_messages[-1]
    continue          # 带着新消息重新想
```

配置项 `planner_interrupt_max_consecutive_count`：最多被重新打断几次。

真人正在打字，你又发一条，他会删掉重写。麦麦做了这件事。
我们现在是：请求发出去就锁死，中途来消息只能排队等下一轮。

## 四、`wait` 是一等公民动作，但有配额

`builtin_tool/wait.py` —— Planner 可以显式调用 `wait(seconds=N)`：

```
"当前对话循环进入等待状态，将固定等待 N 秒；
 期间收到的新消息不会提前打断本次等待。"
```

注意**「不会提前打断」**：她决定晾你 30 秒，这 30 秒就是真的。

但连续 wait 有上限（默认 3 次），到顶后 wait 工具直接拒绝：

```
"连续 wait 已达到上限，本次不再进入等待；
 视为多次等待后仍无后续，当前对话进入休息。"
```

防的是「她一直等一直等，永远不说话」的死循环。

## 五、注意力漂移 —— 显式建模「人会走神」

`maisaka/attention_drift.py`。这个模块我完全没想到会存在。

四档漂移强度（subtle / active / scattered / wild），
三种回钩策略（strict / balanced / loose），
三种短反应风格（reserved / natural / lively）。

`wild` 档的原文：

> 漂移档位：强烈跳跃。你可以先被最有趣的细节劫走一下，出现短促插话、
> 突然联想或半路拐弯；但每轮最多一次明显跳跃，不能无视明确提问，
> 最后要让人看得出你在接哪条消息。

**这直指我们「太得体所以有距离感」的病根。**

我们的女主每一句都在精准回应玩家上一句。这是客服的行为模式，不是恋人的。
真人聊天时注意力会被劫走——你说到「昨天在便利店」，她可能整段回复
都在讲那家便利店的关东煮，把你原来的问题忘了。

而且他们把边界划得很清楚，有两条反向约束：

> - 表现活跃联想，**不要真的降效**；不要为了显得分心而故意拖延、忽略任务。
> - **不要医学化描述这种风格，不要自称 ADHD，也不要主动声明自己分心。**

第一条是把「像人」和「变笨」分开——这是所有拟人化最容易踩的坑。
第二条是禁止元叙述，跟我们 postprocess 里剥旁白是同一类防御。

## 六、决策 / 发言分离

`maisaka_chat.prompt`（Planner，导演视角）：

> 请注意，**你不是 {bot_name} 本人，不要替 {bot_name} 发言**，
> 你需要给 {bot_name} 的行为做出决策。

Planner 输出的是「分析 + 工具调用」，台词由 `reply` 工具再走一次
`maisaka_replyer.prompt` 生成。两次 LLM 调用。

这么做的收益在**内部多轮**：Planner 可以先 `query_memory` 查记忆、
再 `fetch_history` 翻旧账、最后才 `reply`。工具集：

```
reply / wait / send_emoji / send_image
query_memory / query_person_profile / fetch_history
switch_chat / view_forward_message / tool_search
```

代价是每轮至少两次调用。我们一次到位更快更便宜，这个取舍我仍然认为
在选项制下站得住——但**「她要不要松口」这类判断值得单拆**。

## 七、两阶段表达：先检索，再生成

`expression_select.prompt`：生成台词**之前**，先让模型从表达库里挑：

```
以下是可选的表达情境：{all_situations}
请你分析聊天内容的语境、情绪、话题类型，选择最适合的，最多 {max_num} 个。
{"selected_situations": [2, 3, 5, 7, 19]}
```

而表达库本身是**学来的**（`learn_style.prompt`），格式是
「当 AAAAA 时，可以 BBBBB」，带 `source_id` 可追溯。

对照我们：147 条 voice-samples **全量常驻**在人设卡里。
被选中的 5 条会真的影响输出；混在 147 条里的 1 条约等于不存在。

（这条在 `maibot.md` 已列为优先级 1，这里补充的是它有向量索引：
`chat/replyer/expression_vector_index.py`，1683 行。）

## 八、行为学习闭环：场景 → 行为 → 结果，带奖励预测误差

三个 prompt 串成环，学的**不是说话风格，是行为策略**：

```
learn_behavior              从聊天里抽「场景-行为-结果」
       ↓
evaluate_behavior_feedback  这个行为做出去了吗？效果如何？
       ↓
consolidate_behavior        好的巩固，坏的抛弃
```

`learn_behavior` 的抽象规则写得很讲究：

> - action 应抽象到「相似场景下还能再次执行」的粒度，保留行为结构，
>   **不要绑定一次性对象、具体型号、临时梗词、截图内容或某个专名**。
> - outcome 要写「补充关键信息」「情绪缓和」「继续追问」这种可观察的互动变化，
>   **不要只写「氛围活跃」这种泛泛结果**。

`evaluate_behavior_feedback` 里直接用了 RL 的语言：

> score_delta **类似奖励预测误差**：
> success 用 0.5 ~ 1.0；partial_success 用 0.1 ~ 0.35；failed 用 −0.4 ~ −1.0。

而且要求 `adopted` 必须有 SELF 消息作为证据——**先证明她真的照做了，
再评估效果**。不然会把「没执行」和「执行了但没用」混为一谈。

## 九、回复效果打分（ASI）—— 里面有 `uncanny_risk`

`maisaka/reply_effect/`。每条 reply 发出去后登记为 pending，
观察后续用户消息，然后结算：

```
ASI = 0.45 × 行为满意度 + 0.35 × 感知质量 + 0.20 × (1 − 摩擦)
```

**行为满意度**（纯规则，不花 token）：

```python
0.30 × 对话继续了 2 轮
0.25 × 下一条用户消息的情绪
0.20 × 用户展开程度   clamp((平均长度 − 8) / 42)
0.15 × 没有出现纠正   （"我是说" "你理解错" "我问的是"）
0.10 × 没有中止       （"算了" 或 两次以上负面词）
```

**感知质量**（LLM rubric，1–5 分）：

```python
0.35 × social_presence   社会临场感
0.25 × warmth            温暖
0.25 × competence        能力
0.15 × appropriateness   得体
```

**摩擦**：

```python
0.40 × 明确负面
0.30 × 修复循环
0.30 × uncanny_risk      ← 恐怖谷风险
```

judge prompt 里对它的定义：

> `uncanny_risk` 的 1 = 完全不怪，5 = **非常过度拟人 / 越界 / 油腻**。

**这是整份代码里我最意外的一个东西。** 他们把「太努力扮人反而恶心」
做成了一个会扣分的显式指标。

我们的 critic 现在评的是「像不像她」「有没有情绪价值」——
全是**正向**维度。缺一个反向的：她有没有用力过猛。
AI 女友这个品类，「油腻」比「平淡」致命得多。

## 十、记忆：写入时就想好「什么时候会用到」

`mid_term_memory_summary.prompt` —— 短期上下文被裁掉的消息压成回想时，
除了 `summary` 还要输出 `recall_cues`：

> `recall_cues` 输出 3-5 个用于之后语义匹配的查询式段落。
> 请额外思考**「什么情景下可能会需要这些信息」**
> 「这些信息和什么内容、人物、任务、关键词关联」，
> 每条写成自然语言短句，包含可匹配的场景、意图或关联内容。

**这是写入时生成检索键，不是读取时算相关度。**

我们的 `memory/retrieval.py` 是读取时三因子打分
（recency + importance + 1.5×relevance）。检索键就是内容本身，
所以「胃病」和「胃疼」要靠 `_content_chars` 打补丁去桥接。

写入时让模型自己写「这条在什么场景下该被想起来」，
等于把桥接工作交给了理解语义的那一方，而且**只做一次**。
成本几乎为零（本来就在调 LLM 做压缩），收益是检索质量。

## 十一、打字延迟

`chat/utils/utils.py:697`：

```python

单个中文字 → 3 倍时间（"嗯" 要打 0.9 秒）
```

# 对我们的意义

先说清楚**不适用**的部分，免得照搬：

- 大量机制是**群聊专属**（@、提及、群体压力、存在感占比）。我们是 1:1。
- 空闲退避 `if not is_group_session: reset()` —— 私聊里直接关掉的。
- 她**没有关系阶段、没有好感度、没有主线**。这三样是我们的结构性优势，
  麦麦的「关系」只是一个 person_profile 印象文本。
- 学习闭环在单人场景反馈信号弱——**但我们有选项**。玩家选了哪个选项，
  是比群聊里「有没有人接话」强得多的监督信号。这点我们比他们有利。

## 能直接搬的，按性价比排

| | 抄什么 | 改哪 | 成本 | 为什么 |
|---|---|---|---|---|

| 2 | **`uncanny_risk` 反向维度** | `evals/critic.py` | 很低 | 我们的 critic 全是正向维度，测不出「用力过猛」 |

## 一个需要想清楚的冲突

**「回复必要性」在选项制下不能照搬。**

麦麦可以不回，因为那是自由聊天。我们是玩家点了一个选项——
点完她不吭声，玩家第一反应是「卡了」，不是「她在生气」。

正确的迁移不是「回不回」，而是**把这套评分变成回复体量与时机的调节器**：

```
高分  →  多条、快、主动追加话题
中分  →  一条、正常速度
低分  →  一条很短的、慢，或者只发一个表情
极低  →  「已读」但把回复推到下一个时间窗   ← 这个要 UI 配合才不像 bug
```

关键是**低分状态必须在 UI 上可见**（正在输入 / 已读 / 稍后回复），
否则「她没回」和「程序坏了」在玩家那里是同一件事。

## 一句话

麦麦教我们的不是怎么写台词，是：

> **活人感的大头不在她说什么，在她"没在说"的那些时刻里，
> 而且那些时刻大部分可以用不花钱的规则做出来。**
