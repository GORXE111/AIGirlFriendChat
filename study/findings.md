# 同类项目研究：他们有什么我们没有

读了 SillyTavern（角色扮演前端事实标准）、letta（原 MemGPT）、mem0（记忆层）。

**结论：四个机制值得抄，其中两个直指我们当前的痛点。**

---

## 一、指令位置：放在历史**之后**

**这是最大的发现。**

SillyTavern 的角色卡 V2 有两个字段我们完全没有对应物：

```
post_history_instructions   // 放在对话历史「之后」的指令
extensions.depth_prompt {
    depth: 4,               // 从末尾数第 N 条消息处插入
    prompt: "...",
    role: "system"
}
```

它们解决的是同一个问题：**上下文越靠后的指令，模型遵守得越好。**

我们现在的消息顺序是：

```
[system] 稳定前缀（人设 12.5k tokens）
[system] 易变层（状态 + 规则 + 输出规格）
[user]   对话记录 + 「按上面的规格输出 JSON」
```

**所有规则都在历史之前。** 一条「不要三条都是照顾型」的规则，
埋在 12.5k tokens 的开头，跟紧贴输出位置说一遍，效果差很多。

而且这解释了一个现象：我每次加规则，效果都递减 ——
不是规则写得不好，是**位置越来越深**。

### 能怎么用

把**最容易被违反的几条**移到对话记录之后，作为最后一条消息：

- 三条选项必须是三个关系动作
- 她的消息不超过 N 字
- 不许编造没发生过的事

稳定前缀留人设和背景（那些不需要"顶着说"），
末尾放**这一回合的硬约束**。

⚠️ 注意与缓存的关系：末尾指令不影响前缀缓存（它在最后），
所以这个改动**几乎零成本**。

## 二、World Info：关键词触发的按需注入

SillyTavern 的 lorebook 条目结构：

```js
{
  keys: ["面馆", "辣酱"],        // 命中才注入
  secondary_keys: [...],          // 二级条件
  constant: false,                // true = 永远注入
  selective: true,
  insertion_order: 100,
  position: "before_char",
  extensions: {
    depth: 4,                     // 插在哪
    probability: 80,              // 概率注入！
    scan_depth: 2,                // 往前扫几条消息找关键词
    match_whole_words: true
  }
}
```

**我们是全量注入**：人设卡 12.5k tokens，每一次调用都带上全部规则 ——
包括她此刻用不到的（健康话题禁令、越界处理、告别语分阶段…）。

这既是成本问题，更是**注意力稀释**问题。我在 loader 里写了体量告警，
但没解决根因：**该按需注入的东西被做成了常驻。**

### 能怎么用

`persona/manifest.py` 已经是按小节抽取，只差一个触发条件。加上：

```python
Section("lexicon.md", ("健康话题专项",), keys=("胃", "疼", "药", "医院", "难受"))
Section("edge-cases.md", ("2. 越界／性化内容",), keys=(...))
```

保守估计能砍掉三到四成常驻体量，而且**留下的规则更显眼**。

`probability` 那个也很妙 —— 有些行为（比如撤回）本来就该是概率性的，
现在我们用 `retract_rate` 在代码里掷骰，其实可以统一到注入层。

## 三、记忆要能改和删，不能只追加

mem0 的记忆管理是四个操作，不是一个：

```
ADD     新事实
UPDATE  已有的事实变了
DELETE  已有的事实被推翻
NONE    重复或无关，不动
```

**我们只有 ADD。** `add_fact()` 是 `INSERT OR IGNORE`。

后果很具体：她今天学到「他喜欢喝冰的」，两周后他说「我胃不好不能喝冰的」，
**两条会同时存在**。检索时两条都可能被选中，于是她说出自相矛盾的话。

聊得越久越严重 —— 这是长期体验的定时炸弹，现在测不出来是因为
自动对局每次都开新档。

### 能怎么用

慢回路抽取事实时，先取出已有事实一起给模型，让它输出操作而不是纯新增：

```json
{"facts": [
  {"op": "UPDATE", "old": "他喜欢喝冰的", "content": "他胃不好，不能喝冰的"},
  {"op": "ADD", "content": "他周五要补课"}
]}
```

---

## 四、记忆块要有容量上限

letta 的 `Block` 有 `limit`（字符数上限）。超了就必须压缩，
逼着 agent 主动整理而不是无限堆积。

我们的 `facts` / `episodes` 表没有任何上限。检索层做了打分（好事），
但底层数据会无限增长 —— 一年后一个存档几千条事实。

### 能怎么用

给 facts 设一个软上限（比如 80 条）。超了就在慢回路里合并：
把五条关于胃的事实压成一条。

这跟第三点是一套 —— 都是「记忆需要维护，不只是积累」。

## 顺带：角色卡 V2 里我们没有的字段

| 字段 | 用途 | 我们 |
|---|---|---|
| `first_mes` | 开场白 | 有（桥段） |
| `alternate_greetings` | 多个开场白轮换 | **没有** |
| `mes_example` | 对话范例 | 有（样本库） |
| `scenario` | 场景设定 | 有（relationship.md） |
| `post_history_instructions` | 历史后指令 | **没有** ← 见第一条 |
| `depth_prompt` | 定深注入 | **没有** ← 见第一条 |
| `talkativeness` | 话痨程度 | 有（max_messages） |

`alternate_greetings` 值得抄一个小的：她主动发起时，
开场白从一组里挑而不是每次现生成，能避免"每次开场都差不多"。

---

## 优先级建议

| | 改动 | 成本 | 收益 |
|---|---|---|---|
| 1 | **历史后指令** | 很低（挪位置） | **高** —— 直接提升规则遵守 |
| 2 | **记忆增删改** | 中 | 高 —— 修一个长期体验的定时炸弹 |
| 3 | 关键词按需注入 | 中 | 中高 —— 砍体量 + 减稀释 |
| 4 | 记忆容量上限 | 低 | 中 —— 配合 2 |

第一条应该立刻做，因为它**几乎零成本**，而且能解释我们一直遇到的
「加了规则但不管用」。
