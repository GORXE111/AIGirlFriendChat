# 麦麦 MaiBot —— 中文圈最对口的那个

`Mai-with-u/MaiBot` · GPL-3.0 · 57M · **今天还在提交**

它的自我定位跟我们几乎一字不差：

> 「不追求完美，不追求效率，追求**温暖、真实**」的数字生命，
> 「模仿人们说话的方式，学习新的梗和群内黑话，持续进化」

场景不同（QQ 群聊 vs 一对一恋爱），但**目标完全一样：活人感**。
架构比我们完整，有三个机制值得直接学。

---

## 一、表达库：情境 → 表达，而且是**学来的**

`learn_style.prompt` 从聊天记录里提取说话方式，格式是配对：

```
请总结成如下格式的规律：当 "AAAAA" 时，可以 "BBBBB"。

[
  {"situation": "对某件事表示十分惊叹", "style": "使用 我嘞个xxxx", "source_id": "3"},
  {"situation": "表示讽刺的赞同",       "style": "使用 对对对",      "source_id": "4"}
]
```

几个细节做得很讲究：

- **`source_id` 可追溯** —— 每条表达都能回到原始那句话
- 明确要求「不要涉及具体人名和名词」—— 抽的是**模式**不是内容
- 明确「不要学习 SELF 的发言」—— 否则会自我强化，越学越怪
- 数量硬上限（3–5 条，不超过 10）

### 但真正关键的是**怎么用**

`expression_select.prompt`：**生成回复之前，先从表达库里挑**。

```
以下是可选的表达情境：{all_situations}

请你分析聊天内容的语境、情绪、话题类型，
从上述情境中选择最适合当前聊天情境的内容，最多 {max_num} 个。

{"selected_situations": [2, 3, 5, 7, 19]}
```

**两阶段：先检索，再生成。**

我们是把 147 条样本**全量常驻**塞进人设卡。他们是按语境选出几条再用。

这既省 token，更重要的是**被选中的那几条会显著影响输出**，
而混在 147 条里的一条基本等于没有。

> 这跟我在 `findings.md` 里写的「注意力稀释」是同一个病，
> 但 MaiBot 的解法比 SillyTavern 的关键词触发更聪明 ——
> **让模型自己判断哪几条适用**，而不是靠关键词命中。

## 二、行为反馈闭环

三个 prompt 组成一个环：

```
learn_behavior           → 从聊天里学到一个行为
       ↓
evaluate_behavior_feedback → 这个行为做出去，效果好不好
       ↓
consolidate_behavior     → 好的巩固，坏的抛弃
```

外加 `expression_evaluation`（评估表达好不好）。

**我们完全没有这一层。** 我们的样本库是死的 —— 我写进去就永远在那，
无论她用了之后效果如何。

这条对单人恋爱游戏怎么用还要想：群聊有「别人的反应」当反馈信号，
我们只有玩家一个人。可能的信号：玩家选了哪个选项、好感变化、
玩家是不是很快就换话题。

## 三、中期记忆

`mid_term_memory_summary.prompt` —— 正是我之前对标 Nomi 时说「我们缺」的那一层。

我们现在是：

```
短期  transcript
长期  facts / episodes / insights
中期  ❌
```

中期记忆管的是「**这周正在发生、还没结束的事**」。
我们的 threads（悬念事项）算是补上了一部分，但那只覆盖「未了结的约定」，
不覆盖「她这周在准备考级，情绪一直紧绷」这种**跨天的状态线**。

## 四、其他值得一提的

**`memory_fuzzy_modify_plan`** —— 记忆的模糊修改。
跟 mem0 的 UPDATE 是一回事，印证了 `findings.md` 第三条：
**记忆必须能改，不能只追加。** 两个成熟项目都做了，我们没有。

**黑话学习三件套** —— `learn_jargon` / `jargon_inference_with_context` /
`jargon_compare_inference`。群聊场景刚需，恋爱游戏用不上，
但「有上下文推断」和「仅内容推断」分开做这个思路值得记住。

**`heuristic_memory_impression`** —— 印象记忆，跟我们的 insights 对应。

**主 prompt 的一个反直觉设计**：`maisaka_chat.prompt` 里明写

> 「**请注意，你不是 {bot_name} 本人，不要替 {bot_name} 发言**，
> 你需要给 {bot_name} 的行为做出决策」

它把「决策」和「发言」拆成两步 —— 决策层是第三人称的导演视角，
真正说话要通过 `reply` 工具。我们是一次调用直接产出台词。

孰优孰劣不好说：拆开更可控，但多一次调用；我们这种一次到位更快更便宜。
不过**「决策 / 表演」分离**这个思路，在需要她做复杂判断时（比如闹别扭时
到底要不要松口）可能有用。

## 优先级

| | 学什么 | 成本 | 收益 |
|---|---|---|---|
| 1 | **表达库检索式 few-shot** —— 样本从全量常驻改成按语境选 | 中 | **高**，直接治注意力稀释 |
| 2 | 中期记忆 | 中 | 中高 |
| 3 | 反馈闭环 | 高 | 中（单人场景信号弱） |

第 1 条跟 `findings.md` 里的「历史后指令」和「关键词按需注入」是一套的 ——
**核心都是：别把所有东西一直摆在那，该用的时候再拿出来。**
